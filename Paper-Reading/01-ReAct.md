# ReAct：把“思考”和“行动”接成闭环

论文：[ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629)

官方代码：[ysymyth/ReAct](https://github.com/ysymyth/ReAct)

## 一句话结论

ReAct 的关键不是让模型生成更长的思维链，而是让语言推理与外部行动交替发生：推理决定下一步去哪里获取证据，环境反馈又迫使模型更新计划。

## 1. 论文试图解决什么问题

在 ReAct 之前，两条路线经常被分开研究：

- **Reasoning-only**：模型在内部生成 Chain-of-Thought，然后直接给答案。优点是能分解问题；缺点是推理建立在模型记忆上，错误事实会沿链条传播。
- **Act-only**：模型直接在环境中选择动作。优点是能获得真实反馈；缺点是缺少显式工作记忆和高层规划，容易重复动作、丢失子目标。

ReAct 的问题意识是：如果推理和行动各自都有明显缺口，能否把它们放进同一条轨迹，让二者相互校正？

## 2. 核心机制

普通 agent 在时刻 `t` 根据历史上下文选择环境动作 `a_t`。ReAct 把动作空间扩展为两类：

- **Thought**：语言空间中的内部动作，不改变外部环境，但把计划、证据摘要、异常处理等信息写回上下文。
- **Action**：真正影响环境的动作，例如搜索、点击、移动或最终提交。

环境执行 Action 后返回 **Observation**。于是轨迹变成：

```text
Task
  -> Thought: 当前目标与缺失信息是什么？
  -> Action:  调用一个外部工具
  -> Observation: 工具返回了什么？
  -> Thought: 新证据是否支持原计划？要不要改路？
  -> Action:  下一步动作
  -> ...
  -> Finish
```

Thought 在论文中承担了多种角色：任务分解、记录进度、从观察中抽取证据、补充常识、重写搜索词、处理异常、综合最终答案。对长程决策任务，Thought 不必每步都出现；稀疏而关键的推理反而更有效。

## 3. 实验怎样验证这个想法

论文覆盖两类任务：

### 知识密集型推理

在 HotpotQA 和 FEVER 中，模型可调用一个很小的 Wikipedia API：`search[entity]`、`lookup[string]`、`finish[answer]`。这不是强检索器，而是刻意受限的接口，用来观察模型能否通过显式推理决定“下一条证据去哪里找”。

结果呈现了很有价值的互补性：

- ReAct 比 Act-only 稳定，说明显式推理确实能指导行动。
- ReAct 在 FEVER 上优于 CoT，但在 HotpotQA 上略低于 CoT。
- ReAct 更少凭空编事实；CoT 的推理结构更灵活，却更容易在错误事实上继续推演。
- 把 ReAct 和带 self-consistency 的 CoT 组合，效果优于单独使用任一方法。

这说明外部证据并不会自动解决所有问题。检索让推理更 grounded，但受限的行动格式也可能降低推理灵活性。

### 长程交互决策

在 ALFWorld 和 WebShop 中，ReAct 需要连续执行多步动作。论文报告：ALFWorld 最佳 ReAct 设置成功率为 71%，明显高于 Act-only 的 45%；WebShop 成功率为 40.0%，比此前最佳结果高约 10 个百分点。这里最重要的现象不是具体分数，而是 Thought 帮助模型维护子目标、追踪已完成步骤、在探索失败后重新规划。

## 4. 失败模式比成绩更值得看

ReAct 揭示了后来 Code Agent 仍常见的四类失败：

1. **循环**：模型重复上一条 Thought 和 Action，无法从无效反馈中跳出。
2. **坏检索拖垮后续推理**：无信息的 Observation 会让模型在错误方向继续投入预算。
3. **错误被显式化但未被纠正**：可读的 Thought 便于诊断，不代表模型一定能自我修复。
4. **步数增加不等于效果提高**：论文在 QA 任务上设置有限步数，因为更多步骤没有继续带来收益。

这直接对应 Code Agent 中的“反复 grep 同一关键词”“重复运行同一失败测试”“连续修改错误文件”“预算耗尽后仓促提交”。

## 5. 映射到 Code Agent

把论文中的概念替换成代码任务，就得到最小 coding-agent loop：

| ReAct 概念 | Code Agent 中的对应物 |
| --- | --- |
| Task | GitHub issue、用户需求、仓库约束 |
| Thought | 故障假设、定位计划、测试策略、变更影响分析 |
| Action | 搜索、查看文件、编辑、运行命令、执行测试 |
| Observation | 搜索结果、源码片段、编译错误、测试日志、git diff |
| Finish | 提交 patch 和验证摘要 |

一个实用实现不必保存或展示无限长的自由文本 Thought，但必须保留它所承担的状态功能：当前假设、已知证据、下一步目的、完成条件和失败计数。

## 6. 自己实现时的设计清单

- 每次工具调用前，要求 agent 明确“此动作要验证哪个假设”。
- Observation 不要原样塞回上下文；保留命令、退出码、关键错误和有限上下文。
- 对相同动作、相同参数连续出现设置循环检测。
- 为搜索、编辑、测试分别设预算，而不是只设一个总 token 上限。
- 每轮编辑后检查 diff，并优先运行最小相关测试，再扩大到回归测试。
- `finish` 前做独立门禁：是否真的改了文件、相关测试是否通过、是否留下临时文件。

## 8. 读完应该带走什么

ReAct 给 Code Agent 的不是完整架构，而是一条最小定律：**模型能力只有经过“行动—反馈—修正”闭环才能落到真实环境中；但闭环本身也会制造循环、噪声和成本，所以必须由接口、预算和验证机制约束。**
